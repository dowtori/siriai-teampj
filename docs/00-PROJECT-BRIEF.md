### 1.3 마스터시트 스키마 (34컬럼 / 4영역)

| 영역 | 컬럼 |
|---|---|
| **프로젝트 정보** | UV(캠페인코드, 예: `260202`), 상태, 캠페인명, 귀속년월, 캠페인 디테일, 주체, 국가, 거래처명, 모집 링크, 응답 링크, 가이드 링크, 캠페인 진행시트, 콘텐츠 검수 시트 |
| **마감일정 관리** | 납품예정일, 시작일, 종료일, D-day |
| **콘텐츠 업로드 관리** | 컨펌율, 제공 수, 선정 수, 업로드 수, 잔여, 업로드율, 비고, 피처링 보고서 |
| **매출 영역** | 입금예정액, 매출(공급가), 원고료, 순이익, 마진율, 견적서 발급일, **세금계산서 발급일**, 입금상태, 특이사항 |

- `UV`는 `YYMMNN` 형태의 캠페인 코드지만 **후반 레코드에는 비어 있음** → 채번 규칙이 무너져 있음. 신규 시스템에서 재부여 필요.
- `상태`는 `8. 완전 종료` / `7. 상시 진행` / `기타/이슈`만 실사용 → **1~6번 단계가 정의는 되어 있으나 시트에 반영되지 않음.** 실제 파이프라인 단계 정의를 다시 받아야 함.
- **매출 인식 기준 = `세금계산서 발급일`** (요청사항과 일치). `견적서 발급일`과 별도 컬럼으로 존재.

### 2.3 ⚠ 데이터 층위 설계의 핵심 발견

**(1) `폴더` 컬럼이 사실상의 세그먼트 태깅이다 — 총 40개 세그먼트**

실제 값 예시:
- `한국거주 일본 유튜버(크레딧 소진 완료)` 342
- `오드타입 인플루언서_뷰티/릴스 (4476 ~ 9550)` 1,000
- `일본 댄서 DM용 1000-6800팔로워` 994
- `뷰티(메일용)(02/27)(사용완료)` 849
- `4월 뷰티 메일용 (무신사) (사용완료)` 667
- `일본 틱톡 댄스(적합도 있음)` / `(적합도 낮음)` / `(적합도 있음 유사군)`

→ 폴더명 안에 **캠페인/브랜드 · 카테고리 · 팔로워 구간 · 소진 여부 · 적합도**가 문자열로 뒤엉켜 있음. 이걸 **정규화된 태그 축(brand / category / tier / purpose / status / fitness)으로 분해**하는 게 백엔드 초기 작업의 핵심.

**(2) `협업상태` 컬럼은 전 레코드 값이 `1` — 즉 미사용이다**

→ **"협업 이력이 있는 풀"은 raw 안에 존재하지 않는다.** 오직 캠페인 진행시트·검수시트에만 있음.
→ 따라서 데이터 층위는 이렇게 나온다:

```
Layer 0  raw pool          20,347   Nox 원본 전체
Layer 1  contactable        9,532   이메일 보유 (= 컨택 가능풀)
Layer 2  contacted            ~     이메일 상태 2·3 (발송/응답) — IG 4,505 / YT 316 / TT 1,108
Layer 3  responsive           ~     답장 활성도 등급 보유 (IG 8,725 / YT 564 / TT 1,067)
Layer 4  collaborated         ★     진행시트·검수시트에서 역추출 (= 협업 이력 풀)  ← 신규 구축
Layer 5  verified             ★     실명·연락처·주소·정산정보 확보 (= 즉시 투입 가능풀) ← 신규 구축
```

**(3) 조인 키 문제 — 최대 기술 리스크**

| 소스 | 식별자 |
|---|---|
| Nox raw | `핸들(@아이디)`, `채널/계정 ID`, `내부ID(997)` |
| 진행시트 | 표시명 + **Instagram URL** |
| 검수시트 | **성함(실명)** + 연락처 + 주소 |

- 표시명은 이모지·특수문자·변경이 잦아 조인 키로 못 씀 (예: `채✴︎연`, `솔 ʚ₍ᐢ. .ᐢ₎ɞ`, `지니🧞‍♂️`)
- **유일하게 안정적인 키는 정규화된 Instagram/채널 URL** → `instagram.com/{handle}` 소문자·trailing slash·쿼리 제거 후 매칭
- 실명↔핸들 매핑은 검수시트에만 존재 → 이걸 살려야 "동일인이 여러 캠페인 참여" 집계가 가능
- 팔로워 수치가 시트에 `86,750`처럼 콤마 포함 텍스트로 들어가 파싱 시 컬럼 밀림 발생 → 마이그레이션 스크립트에서 방어 필요

## 3. ⚠ 개인정보 처리 — 착수 전 반드시 결정

검수시트/진행시트에 다음이 **평문으로** 들어 있음:

- 실명 (성함)
- 휴대전화번호
- **자택 상세주소 + 우편번호** (제품 배송용)
- 정산자료 (슬랙으로 수령 → 주민등록번호·통장사본 포함 가능성 높음)

현재는 구글시트 링크를 아는 사람이면 접근 가능한 구조. 시스템 이식 시 **오히려 개선 기회**지만, 설계에 반드시 반영해야 함:

- [ ] 민감 컬럼 암호화 (Postgres `pgcrypto` 또는 앱 레벨 봉투 암호화)
- [ ] RLS + 역할별 마스킹 (일반 담당자에게는 주소 뒷자리 마스킹)
- [ ] 접근 로그 (누가·언제·누구의 개인정보를 조회했는가)
- [ ] 보유기간 / 파기 정책 (캠페인 종료 + N개월)
- [ ] 개인정보 수집·이용 동의 플로우 (인플루언서 페이지에서 전자 동의로 대체 가능)
- [ ] 주민등록번호는 **원천징수 목적 법적 근거**가 있을 때만 수집, 별도 암호화 저장

```

   → verifyCode(code)  서버 액션
   → normalizeCode → lookupCompany  (서버 전용 레지스트리)
   → recordEntry (접속 로그 → 웹훅 → 시트)
[개인화 /space/[code]]  서버 컴포넌트
   → 클라이언트로는 { code, brand, segment } 만 전달 (연락처 제외)

크리에이터 지표는 현재 **핸들 기반 목업**(`docs/ARCHITECTURE.md` 명시) → 실데이터로 교체 대상.

  │                 │                        ├── shipment            ├── influencer_identity (플랫폼별 계정)
  │                 │                        ├── content_submission  ├── influencer_metrics_snapshot
  │                 │                        ├── review_checklist    ├── influencer_pii (암호화)
  │                 │                        └── payout              └── influencer_tag (세그먼트)
  │                 │
  │                 ├── campaign_deliverable (제공/선정/업로드 수)
  │                 └── campaign_finance (매출·원고료·순이익·계산서발급일·입금상태)
  │
  ├── brand_contact
  └── brand_access_code ──► 브랜드 페이지 / 광고 랜딩

access_log · notification_log · audit_log
```

핵심 설계 원칙:
- **`influencer`는 사람, `influencer_identity`는 계정.** 같은 사람이 IG/YT/TT를 동시에 가질 수 있고, 실제 raw에도 `소셜미디어` 컬럼에 복수 URL이 파이프(`|`)로 들어 있음
- **`campaign_participation`이 시스템의 심장.** 진행시트 1행 = 이 테이블 1행. 검수 체크리스트가 이 행의 상태 컬럼들
- **재무는 캠페인 단위로 분리.** 매출 인식은 `tax_invoice_issued_at` 기준

### 6.3 3개 서피스

1. **파이프라인 단계 정의** — 시트의 `상태`가 `8. 완전 종료`/`7. 상시 진행`만 실사용. 1~6번의 실제 정의는? 어드민 캠페인 보드의 컬럼이 됩니다.
